## 三、关键根因（三个"修了也不生效"的坑）

这三个是本轮真正的价值所在——它们不产生报错，只让修复在线上静默失效。

### 坑 1：沙箱复用旧 `.next`，启动器以为「已构建」

`server.cjs` 原来只判断 `.next/BUILD_ID` 存不存在。发布平台会**复用上一次的沙箱**，旧产物一直在，于是永远跳过编译，线上跑的是历史代码。

**证据**：源码已改为 4 板块，线上接口仍返回 `sections: 1`；重新部署后依旧如此。

**修法**：新增 `scripts/build-meta.cjs`，用**源码内容哈希**（85 个 src 文件 + 配置 + seed，约 80ms）与 `.next/.src-hash` 比对，不一致就重建。构建成功即落指纹（`scripts/stamp-build.cjs`，已挂进 `npm run build`）。

不用时间戳的原因：发布流程解压会把 mtime 重置，用"谁更新"判断必然误判。

### 坑 2：云端超时把正常的长回答腰斩

`streamCloudChat` 原来用 `Promise.race([consume, timeoutAfter(8000)])` —— 8 秒**盖住整个流**。写作批改动辄 2000+ 字，8 秒必被切断；更糟的是被切断时如果已经吐过字，会 `return local` 把半截答案当完整答案返回。

**修法**：改成"首字护栏"——只在**一个字都还没来**时计时，首字一到立刻撤销，长回答正常流完。另加：

- 换模型时 abort 掉上一个残留的流，防止旧流增量污染新答案；
- 候选列表、模型列表、每次尝试结果都打日志，线上排查不用靠猜。

### 坑 3：`/api/papers/[id]` 仍是 v1 结构

把所有 passage 塞进一个伪造的 `reading` section，`sections.length === 1`、类型全错、题目 id 对不上。该接口在 `src/` 内无调用方（练习页走 Prisma 直查），属对外结构错误，已改成与练习页一致的 Section 层级映射，老数据仍回退单 section。
